# StudyApp — project conventions

Personal study environment (flashcards + spaced repetition first; materials, calendar, AI generation later). Single local user; auth is config-gated (see below) and off by default for local dev. The user (Alex) reviews and steers; see README for product roadmap.

## Stack & layout

- .NET 10, C#. Blazor Web App with **global interactive server** rendering — no API layer; components call services directly.
- `src/StudyApp.Core` — pure domain (entities, SM-2 scheduler, due policy, session queue, import parser). **No web or EF dependencies. Keep it that way.**
- `src/StudyApp.Web` — Blazor UI, EF Core (SQLite) in `Data/`, thin services in `Services/`.
- `tests/StudyApp.Core.Tests` — xUnit. All scheduling/parsing logic must be covered here.

## Conventions

- Data access: `IDbContextFactory<StudyDbContext>` per operation; never inject `StudyDbContext` directly (Blazor Server).
- **Any raw `SqliteConnection` opened outside EF must `SqliteConnection.ClearPool(connection)` in a `finally`, not just on the success path.** `Dispose()` returns the native handle to Microsoft.Data.Sqlite's pool instead of closing it, so the process keeps the `-wal` file open. This silently disabled `DatabaseRecovery`: its `quick_check` probe *throws* on a corrupt database (the case it exists for), skipping a success-path-only `ClearPool`, so the very next `File.Move` of the `-wal` failed with "used by another process" on every retry and the app could never start.
- Time: always through injected `TimeProvider` (never `DateTime.Now/UtcNow` in domain logic). "Due" semantics live only in `DuePolicy` — study day rolls over at 04:00 local.
- Soft deletes (`IsDeleted` + global query filters) everywhere; `CreatedAt/UpdatedAt` maintained by `TimestampInterceptor` — never set manually.
- Scheduling changes go through `IScheduler`. FSRS should replace `Sm2Scheduler` behind that interface, never inline in UI/services.
- Schema changes: EF migrations only (`dotnet dotnet-ef migrations add <Name> --project src/StudyApp.Web`). DB file is real user data — backups run at startup, keep it working.
- Markdown rendering: `MarkdownRenderer` only (raw HTML disabled — XSS). LaTeX in card/notes markdown is authored as `$...$` / `$$...$$` — Markdig's math extension (bundled in `UseAdvancedExtensions`) converts that to literal `\(...\)`/`\[...\]` text before KaTeX ever sees it, so `wwwroot/js/mathRender.js`'s auto-render delimiters target `\(\)`/`\[\]`, not `$`. KaTeX is vendored offline under `wwwroot/lib/katex` (pulled via `npm pack katex`, not a CDN).
- File uploads: `Program.cs` sets `AddSignalR(o => o.MaximumReceiveMessageSize = 64MB)` — Blazor Server's `InputFile` rides the SignalR circuit, whose default 32 KB cap otherwise silently blocks anything but tiny files.
- Any `IJSObjectReference.InvokeVoidAsync` called from `OnAfterRenderAsync` against an `@ref` element **must** be wrapped in `try { } catch (Exception ex) when (ex is JSDisconnectedException or JSException) { }`. A rapid re-render (e.g. fast card grading) can make the `ElementReference` go stale between the guard check and the awaited call resolving; letting that exception bubble terminates the whole Blazor circuit, not just the one render — confirmed by reproducing it under a rapid-fire synthetic input stress test.
- Routed pages that map multiple route templates to one component (e.g. `Review.razor`'s `/review`, `/review/course/{id}`, `/review/deck/{id}`) must build their state from `OnParametersSetAsync`, not `OnInitializedAsync` — Blazor reuses the component instance across same-component navigations, so `OnInitializedAsync` only runs once ever. Building session/query state there leaves it frozen on whatever scope loaded first. Guard against rebuilding on every render by comparing the incoming parameters against what was last built.
- **Mixed RTL + LTR + math rendering is owned by the `md-content` class** (rules in `wwwroot/app.css`, global because `MarkupString` HTML carries no CSS-isolation attribute). Any element holding `MarkdownRenderer` output must carry it. It does two things `dir="auto"` alone cannot: `unicode-bidi: plaintext` per block so each *paragraph* resolves its own direction (`dir="auto"` resolves once for the whole container, so a card starting with an English line lays out its Hebrew wrongly), and `direction: ltr; unicode-bidi: isolate` on `.katex`/`.math` because KaTeX ships no direction rule of its own and otherwise inherits `rtl`, shuffling formula terms and dragging trailing punctuation. `.math` is Markdig's wrapper and survives KaTeX failures, so even unrendered LaTeX stays in logical order. Complementary content rule enforced in the AI prompts: **RTL text never goes inside `$...$`** — it cannot be typeset — and delimiters are plain `$`, never `\$` (also normalized by `ClaudeService.NormalizeMarkdown` before storage).
- **AI is a two-stage pipeline and the stages must not blur.** Ingestion (`IngestionService`) is the *only* code that sends an original file to the model; it produces a `MaterialExtract` that is stored permanently. Everything downstream — card generation today, importance and gap-closing later — reads the extract and never the raw file. That is what keeps repeat runs cheap, so don't "just re-read the PDF" in a new feature. It also means the extract must be able to stand in for the original: LaTeX preserved as `$...$`, source language never translated, figures described in place, page numbers kept for citations. **Extraction has two modes, chosen by `MaterialKind` via `ClaudeService.ModeFor`.** Material the student owns, and assessments whose exact phrasing *is* what's being asked (exams, assignments, their own notes, the syllabus), is transcribed verbatim. Published reference material (book chapters, distributed lecture notes, and `Other` as the safe default) becomes comprehensive study notes instead: every definition, rule, theorem, formula and worked-example method survives in full, formal statements are quoted, and the surrounding prose is reworded rather than reproduced. This is a better fit for what the pipeline downstream actually consumes — mapping reads topics/terms/section titles, generation needs definitions and methods — and it is also what stops a course book being copied wholesale, which the API's output filter will refuse outright (`Output blocked by content filtering policy`, delivered mid-stream). The mode used is recorded in the job's message (`transcribed` / `noted`), not on the extract, so re-classifying a material later doesn't rewrite the history of what was done. Extraction quality is the ceiling on every downstream feature, which is why extracts are viewable and re-runnable at `/materials/{id}/extract` rather than an invisible cache.
- **The course map is a third pipeline stage, and it revises rather than rebuilds.** `CourseTopic` records what a course covers, how much each topic matters (`TopicImportance`: Core/Supporting/Peripheral — tiers, not a score, because the evidence supports an ordering and a number would jitter on every re-run and bury real shifts), and which material evidences it (`TopicSource`, where `Mention = Assessed` is load-bearing: it is what makes a topic examinable rather than merely covered, and it is what `StudyPlanService` scopes an assignment's plan by). Importance is judged against the per-course `Course.AssessmentWeights` profile, which is user-editable because nothing in the material reveals whether a course lives on its final or on weekly assignments. Mapping reads **extracts only** — never original files — which is what keeps a re-map cheap enough to run whenever material is added. `MapCourseAsync` always receives the current map and must reuse surviving names verbatim: topics are long-lived (cards link to them, users pin and dismiss them), so a fresh derivation each run would churn names and orphan everything attached. Model input/output crosses the boundary as short refs (`M1`, `T1`), never GUIDs — a flipped character in an echoed GUID silently detaches a proposal from its evidence. Every run produces a *pending* `CourseMapRevision`; **`MapRevisionPolicy` enforces at apply time what the prompt only requests** (pins, dismissals, self-merges, re-adding an existing topic), re-checked then rather than at generation because a revision can sit for days while the user changes the very topics it refers to.
- **Coverage and mastery are two axes and must never be blended.** `CoveragePolicy` (Core/Planning) answers "do my cards cover the course?"; `ProgressPolicy` answers "how well do I know the cards I have?". A single number would hide which half is the problem, and they call for opposite responses — low coverage means write cards, low mastery means study. `CoreCoverage` is the actionable figure; overall coverage counts peripheral topics and can read reassuringly while everything assessed has nothing behind it. Dismissed topics leave the denominator entirely. `CardTopic` is many-to-many on purpose (one card can legitimately serve two topics). Links arrive either from gap-targeted generation (`CardSuggestion.CourseTopicId`, carried across by `SuggestionService` on approval) or from the separate `JobKind.MapCoverage` job, which only sends not-yet-linked cards — kept out of the mapping prompt because card counts change far more often than the topic set does.
- **Prerequisites are the map's second axis, and `PrerequisiteGraph` owns all of it.** `TopicPrerequisite` is a composite-key edge like `CardTopic` (an edge has no identity beyond the pair it joins), and removing one is the app's only hard delete — a soft-deleted edge would block re-adding the same dependency, since the key *is* the row. `PrerequisiteGraph` (Core/Planning, pure, tested) does the layering: `stage = 1 + max(stage of prerequisites)`, **longest path not shortest**, because a topic is only reachable once *every* prerequisite is. Two rules that look like details and aren't: a **dismissed topic is bypassed, not severed** (in A→B→C with B dismissed, C still rests on A — cutting at B would strand C at the start of the course), and **stage indices are compacted to 0,1,2…** so a cycle that somehow reached the database can't render as "Stage 1, Stage 3". **`TopicChangeKind.Relink` is not optional**: on an already-mapped course a re-map has nothing to add or re-weight, so without it dependencies could never arrive at all. **But `MapCourse` alone will not build a learning path, and `JobKind.MapPrerequisites` exists because of it.** Mapping is a revision prompt that must resist churn — faced with a settled map and no new evidence it proposes nothing, which is right for its job — so it only wires up topics it is currently adding or that sit next to new material. Measured: two real re-maps of a mapped course left 7 of 17 topics unlinked, including round-robin scheduling not requiring CPU scheduling. `RunPrerequisitesAsync` is the opposite instruction (fill the gaps) over a cheap input (topic names, summaries, section titles — never the material), producing `Relink` proposals into the existing review flow, so no part of the apply path changed. It is **additions only** — a hand-drawn edge is never argued with, matching pins and dismissals — and edges that already exist or would close a cycle are filtered when the proposal is *built*, not left to the apply pass, so a proposal can never appear to do nothing. It is deliberately exempt from the pin check — pinning fixes *importance* and says nothing about what a topic builds on. **Edges are resolved in a pass over the whole revision after each accept, never inside one**: `AcceptAllAsync` walks proposals ordered by kind then name, so a prerequisite is routinely accepted *after* the topic needing it, and a forward-only pass drops that edge silently (verified: "Bounded-buffer" sorts before "Counting and binary semaphores" yet depends on it). The pass is idempotent. An accepted `Add` writes back `proposal.CourseTopicId` so the pass can find what it produced, and **`Merge` must rewire edges onto the survivor in both directions** or folding two names for one concept severs every path through it.
- **The progression map's connector lines are drawn, not laid out** (`wwwroot/js/graphEdges.js`). Endpoints are only knowable after the browser has wrapped and sized the stage columns, so JS measures the cards and writes curves into an SVG behind them. The DOM is the entire payload — nodes carry `data-topic` and `data-requires`, so no graph crosses the interop boundary — and a `ResizeObserver` redraws on reflow, disconnected via `disposeEdges` from the component's dispose path. The container is `dir="ltr"` (stages always flow left to right whatever the course's language, or the drawn geometry stops matching the reading order) while each name keeps `dir="auto"`. It scrolls horizontally rather than stacking on a narrow screen: stacked columns put endpoints at opposite edges of the viewport, and the List view is the real answer for a phone.
- **Rendered markdown that sits inline uses `MarkdownRenderer.ToInlineHtml`**, not `ToHtml`. `ToHtml` always emits block HTML, so even a bare topic name comes back wrapped in `<p>` — invalid inside a span, and the browser hoists it out of the flex row it was laid out in. Anywhere a topic name, plan item or proposal name is displayed it is markdown with LaTeX (the mapping prompt asks for it explicitly and `CourseMapService` normalises `\$`→`$` before storing), so it needs the full five-part recipe — block element, `md-content`, `dir="auto"`, `MarkupString`, and a `::deep` margin rule — inside an `@ref`'d container that `OnAfterRenderAsync` hands to `renderMath`. **Adding a surface that shows topic text means adding it to that ternary too**, or the LaTeX stays as `\(…\)`.
- **A `Submission` is a `Material`, and it must never feed the pipeline.** Uploading a solution reuses upload/storage/serving/ingestion for free, but it is excluded from `CourseMapService`'s material bundle *and* from `CardGenerationService`'s course-wide glossary, with `AssessmentWeight` 0. A submission records what the student thinks, not what the course teaches; letting one in would let a confident wrong answer promote a topic or define a term. `JobKind.ReviewSolution` points `MaterialId` at the *submission* and walks back through `Material.SubmissionForId` for the questions, so `GenerationJob` needs no second material slot. `SubmissionReview` carries **no score or predicted grade** — same argument as never blending coverage with mastery: nothing here has seen the marking scheme, and per-question verdicts say it honestly. Findings carry a `CourseTopicId`, which is what makes a mistake actionable rather than prose you read once.
- **`StudyPlanPolicy` is deliberately not an AI call.** Once the map records what an assignment assesses and cards are linked to topics, "what should I do before Maman 12?" is a pure function of data already held — free, never stale, and unit-testable against hand-computed values. It orders by importance first and severity second: a core topic that's slipping outranks a peripheral one you've never touched.
- Anthropic access goes through `ClaudeService` only, using structured outputs (JSON schema) rather than text parsing. The key comes from configuration (`StudyApp__Anthropic__ApiKey`) — never a file, never the database, never the browser. Model default `claude-opus-5`; token usage is recorded on every `GenerationJob` so spend is always visible.
- Generated cards never enter a deck directly — they land in `CardSuggestion` (the inbox) and only become `Card`s on user approval, carrying `SourceMaterialId`/`SourceReference` provenance across.
- Long AI calls run in `JobRunner` (a `BackgroundService`), serially. Never call the API from a component: a multi-minute request would hold the Blazor circuit. Jobs interrupted by a restart are marked Failed at startup rather than left spinning. **The `JobKind` switch throws on an unhandled kind** — it used to fall through, which completed the job successfully having done no work, indistinguishable from a run that worked.
- **Auth is config-gated and lives in `AuthOptions`** (same shape as `AiOptions`): it activates as soon as any sign-in method is configured — `StudyApp__PasswordHash` (PBKDF2, preferred), `StudyApp__Password` (plaintext, dev only), or Google/GitHub OAuth. Local runs with none configured stay wide open on purpose; **any deployment carrying an API key must configure one**, since an open instance doesn't merely leak flashcards, it lets a stranger spend money on generation runs. Non-negotiables when touching this: an OAuth provider without `StudyApp__Auth__AllowedIdentities` **throws at startup** (authentication ≠ authorization — otherwise any Google account on earth is a valid credential); `ReturnUrl` is always passed through the local-only guard; and antiforgery stays enabled — **never re-add `DisableAntiforgery()`** to a sign-in path.
- **`Login.razor` must stay non-interactive.** `App.razor` renders `/login` with a `null` render mode, because `SignInAsync` can only write the auth cookie on a real HTTP response — inside an established SignalR circuit the headers are long gone. It also needs `[AllowAnonymous]`, or the fallback authorization policy protects the login page itself and the cookie handler redirects `/login` → `/login` until the URL overflows (HTTP 414). `AddCascadingAuthenticationState()` is registered unconditionally: `NavMenu`'s `AuthorizeView` throws without it even when auth is off.
- **Progress ("mastery") is owned entirely by `ProgressPolicy`** (`StudyApp.Core/Scheduling`), and is deliberately built only from `Card.IntervalDays`/`Lapses`/`State` and `ReviewLog` — **never `Card.EaseFactor`**, which is SM-2-specific and won't exist once FSRS replaces `Sm2Scheduler` behind `IScheduler`. It's two independent numbers, not one score: `Mastery` (durability — interval scaled against a 21-day maturity threshold, moves only when you study) and `RecallNow` (retrievability — the forgetting curve since last review, decays with elapsed time by design). Collapsing them into one percentage was considered and rejected: it either hides an overdue backlog behind a good number, or makes "progress" fall while the user sleeps. `ProgressPolicy.Aggregate` takes an arbitrary `IEnumerable<Card>` — a deck's cards, a unit's, or a course's — so deck/unit/course rollups are the *same function* over a wider set, never a separate calculation; unit/course numbers are correctly card-weighted (verified: two decks averaging 49%/100% roll up to the course's true 64%, not a naive 74.5% average-of-averages). `Deck.UnitId` (nullable, `SetNull`) is the deck's default unit; `Card.UnitId` overrides it per-card when set. Daily trend snapshots (`ProgressSnapshot`, unique on `(DeckId, CapturedOn)`) are written by `ProgressSnapshotService` — piggybacked on `JobRunner`'s existing startup phase (not a new hosted service) and called directly from `Review.razor` when a session completes (not a queue — a UI-triggered event has nothing to queue onto).
- Uploaded material files are served inline only for an explicit MIME allowlist (`Program.cs`, the `/materials/{id}/file` endpoint) — `text/html` and `image/svg+xml` are deliberately excluded since both can carry same-origin executable script, and `MimeType` is client-supplied at upload time so this allowlist is the actual security boundary. Anything outside it is forced to download via `Content-Disposition: attachment` instead.

## Commands

- Run: `dotnet run --project src/StudyApp.Web --urls http://localhost:5170`
- **Stop the app before building.** A running instance locks its own build output, so `dotnet build` fails with `MSB3027 … locked by StudyApp.Web`: `Get-Process StudyApp.Web -ErrorAction SilentlyContinue | Stop-Process`. Prefer a clean stop over force-killing — a kill mid-write tears the SQLite `-wal`, which `DatabaseRecovery` now quarantines and recovers at startup, but there's no reason to keep exercising it.
- Test: `dotnet test`
- Browser preview: `.claude/launch.json` config `studyapp`
